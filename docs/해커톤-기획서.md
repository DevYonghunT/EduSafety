## 1. 배경과 문제 정의

- 바이브 코딩의 확산으로 교사가 직접 만드는 수업·학급 앱이 급증하고 있다.
- 이 앱들은 학생의 감정 기록·성적·이름 같은 민감정보를 자주 다루지만, 만든 교사도 검증할
  전문성이 없고, 검증해 줄 공적 체계도 없다.
- **'우매한 봉우리' 문제 (더닝 크루거 효과)**: 바이브 코딩은 전문성 없이도 "작동하는 앱"을
  즉시 만들어준다. 화면이 돌아가는 순간 만든 사람은 학습 곡선의 **우매한 봉우리** — 자신감은
  최고인데 자신이 무엇을 모르는지 모르는 지점 — 에 서게 된다. 비밀키 노출, 열린 DB, 학생
  데이터의 외부 전송은 그 봉우리에서 내려다보이지 않는 절벽이다. AI 코딩 도구는 봉우리에
  오르는 비용을 0으로 만들었고, 절벽 아래에 있는 것이 학생의 개인정보다.
  **심사는 개인의 겸손에 기대지 않고, 이 간극을 제도로 메운다.**
- **AI 기본법 시행(원 시행 2026-01-22, 현행 개정본 2026-07-21 시행)**: 유·초·중등 학생
  평가에 쓰이는 AI는 고영향 인공지능으로 분류된다. 학교 현장의 AI 앱은 법이 주시하는 영역이다.
- **초·중등교육법 제29조의2(2026-03-01 시행)**: 학습지원 소프트웨어를 교육자료로 선정하려면
  교육부·개보위가 정한 기준을 지키고 학교운영위원회 심의를 거쳐야 한다(2026학년도 1학기부터
  적용). 그런데 그 '기준 충족 확인'은 업체 자기신고 체크리스트와 학교의 육안 확인에 의존한다 —
  학교에는 코드를 검증할 전문성이 없다. **법이 요구하는 심의의 증거 인프라가 비어 있다.**
- 자가점검 도구의 한계: 자가점검은 "정직한 답변"을 전제하지만, 심사는 "통과하고 싶은
  사람"을 전제해야 한다. 자기신고가 아니라 **증거**가 필요하다.

## 2. 프로젝트 정의와 투트랙 구조

**에듀 세이프(EduSafe)** 프로그램은 **투트랙**이다: 교사에겐 거울, 기관에겐 저울.

| | 트랙 1 — 스킬 (거울) | 트랙 2 — 심사 앱 (저울) |
|---|---|---|
| 사용자 | 제작 교사 (자기 컴퓨터·자기 구독) | 심사자 (교육청·선도교원) |
| 하는 일 | 배포 전 자가점검 — 보안·개인정보 심화, 로컬 전체 접근(빌드·git 히스토리 포함), 행동 중심 보고서 | 제출물 심사 — 코어 루브릭 + 교육적 적절성, SHA 고정, 점수·종합판정, 보완 요청서, 인증마크 |
| 하지 않는 일 | 점수·인증·통과 판정, 교육 적절성 판단, 코드 수정 | 교사 로컬 환경 접근, 스킬 보고서의 무검증 신뢰 |
| 산출물 지위 | **거울** — 인증 증거가 아님 (명시) | **저울** — 공적 심사 기록·인증의 근거 |
| 문서 체계 | 스킬 spec·plan·인수인계 (별도 담당) | 본 기획 문서 3종 |

**공유 자산** (트랙이 아니라 프로그램의 것): 코어 루브릭 정본(통합 예정 — 대조표는
기존 프로토타입 저장소 `docs/루브릭-대조표.md`), 판정 어휘(4값·근거 없는 판정 강등·충돌 시
최악 우선), 법령·근거 카탈로그(기존 저장소 `docs/research/`), 마스킹 규칙, 신뢰 경계 언어.
**변경 규칙: 기준을 바꾸려면 코어를 먼저 — 트랙에서 몰래 항목을 추가·삭제하지 않는다.**

**트랙 간 인터페이스** (로드맵): 스킬의 `edusafe-report.json`을 앱이 **참고 입력**으로
수용하되 신뢰하지 않는다 — 교사 확인 항목을 심사자 확인 후보로 미리 채우고, 스캔은 재검증.

**이번 해커톤 출품 = 트랙 2의 코어 재구축.** 트랙 1(스킬)은 비범위 — 발표에서 투트랙
구조로 언급만 한다.

핵심 원칙 한 줄: *AI가 코드에서 증거를 수집해 판정 초안을 만들고, 최종 판정은 사람이 한다.*

## 3. 사용자와 시나리오

- **1차 사용자(심사자)**: 교육청 담당자·선도교원. GitHub 주소 또는 제출받은 프로젝트 폴더로
  심사를 수행하고 보고서를 발급한다.
- **간접 사용자(제작 교사)**: 심사 보고서와 보완 요청서를 받아 앱을 개선하고 재심사를 받는다.
- 시나리오 (투트랙 전체 여정): 교사가 **스킬로 자가점검·수정**(트랙 1, 거울) → 제출 →
  사전 게이트 통과 확인 → 규칙 스캔 → AI 판정 초안 → 심사자 승인/번복 → 보고서·보완 요청서
  발급 → (보완 후) 재심사 → 인증마크 (트랙 2, 저울).

## 4. 심사 흐름 (5단계)

| 단계 | 내용 | 비고 |
|---|---|---|
| ① 불러오기 + 규칙 스캔 | GitHub 주소 또는 폴더 업로드. 결정적 규칙 40여 종 스캔 | API 키 불필요 |
| ② AI 분류 추론 | 4트랙 중 하나를 근거와 함께 제안 → 심사자 확정 | 학습콘텐츠는 성취기준 태깅 |
| ③ 루브릭 판정 | AI가 항목별 판정 초안 작성 — 근거 코드 인용 강제 | 심사자 API 키 사용 |
| ④ 심사자 승인·번복 | 항목별 확인. 번복은 사유와 함께 기록 보존 | 수동 항목은 직접 판정 |
| ⑤ 보고서 | 커밋 SHA/콘텐츠 지문 고정, 종합 판정, 인쇄/PDF | 보완 요청서 자동 생성 |

4트랙: 교무·행정 자동화 / 교과 수업 도구 / 학습 콘텐츠·활동 / 학급 운영·소통

## 5. 신뢰성 원칙 (설계의 심장 — 코드로 강제)

1. AI 출력은 판정이 아니라 **판정 초안 + 근거 인용**. 근거 없는 충족/미충족은 자동으로
   '판단불가'로 강등한다 (검증 함수가 사후 강제).
2. AI 응답에서 누락된 항목은 '판단불가'로 채운다.
3. 판단불가가 하나라도 남으면 종합 판정은 무조건 **'보류'**.
4. **최종 판정은 심사자(사람)**. 번복은 사유와 함께 기록.
5. 심사는 **커밋 SHA**(폴더 제출은 파일 전체의 SHA-256 콘텐츠 지문)에 고정 — "이 심사는
   커밋 X에 대한 것"이 실제로 성립. 인증 후 수정하면 지문이 달라져 변조가 증명된다.
6. 심사 대상 코드는 신뢰할 수 없는 입력으로 취급 (프롬프트 주입 대비, 텍스트 노드 렌더만).
7. **AI 전송 전 로컬 마스킹**: 데이터 파일(csv 등)은 내용을 외부 LLM으로 보내지 않고 존재만
   고지하며, 탐지된 비밀키는 마스킹 후 전송한다 — 심사 도구가 스스로 개인정보 원칙을 지킨다.
8. **AI 분석 범위의 정직한 고지**: 전송 상한(150k자)에는 우선순위 선별을 적용한다 —
   보안 규칙·설정 → 일반 소스 → 번들·압축·잠금파일(후순위). 제외 파일이 생기면 검토
   커버리지(%)와 제외 목록을 판정 화면과 보고서에 자동 고지한다. 조용한 절단 금지.

## 6. 심사 루브릭 v1.3 (필수 10 + 점수 15 + 수동 6)

판정값: 충족 / 미충족 / 판단불가(사람 확인 필요) / 해당없음.
모든 항목에 **법적 무게 등급**(법률 / 고시·훈령 / 공식 권고 / 모범 사례)을 표기해
보고서에서 "법적 의무"와 "권고"를 섞어 말하지 않는다.
필수 항목이 하나라도 미충족이면 불합격 후보. 트랙 표기: ALL=전 트랙, SF=학생 대면(학습콘텐츠·학급운영), A=교무·행정.

**결과 표현 (점수 폐지 결정)**: 단일 점수 대신 **카테고리별 상태**로 표현한다 — 항목을
스킬과 공유하는 8분류(수집 / 접근·권한 / 비밀·파일 / 제3자 전송 / 화면·로그 / 코드 안전 /
고지·보유·파기 / 학생 안전)로 묶고, 카테고리 상태 = 그 안의 **최악 판정**(필수 미충족=빨강,
점수 미충족=주황, 판단불가=확인 필요, 전부 충족·해당없음=초록). 배점(weight)은 카테고리 내
우선순위 표시로만 쓴다. 종합판정 3값(합격 후보/보류/불합격 후보)은 심사 결정용으로 유지.

**보호 수준 (위험 기반 최소 기준선)**: 앱 간 서열이 아니라, **앱의 기능에서 자동 도출되는
요구 수준**이다 (OWASP ASVS의 수준 개념·교육부 선정기준의 적용대상 논리와 정렬).

- **L0 공통 기본선** (모든 앱, 예외 없음): 비밀키 노출 없음 · 열린 DB 없음 · 주민번호 없음 ·
  https · 인젝션 없음 — **L0 미달 = 배포 부적합**
- **L1 개인정보 보호선** (학생 정보를 수집하면): L0 + 만 14세 동의 · 최소수집 · 처리방침 고지 ·
  타인 데이터 읽기/쓰기 불가 · 삭제 수단 · 저장 위치 고지 · 공용기기 처리
- **L2 민감·공정성 보호선** (민감정보 또는 평가·경쟁 기능이 있으면): L1 + 민감정보 익명화 ·
  위기 안내 · 점수 위조 불가 · 정답 비노출 · 외부 LLM 입력 고지

판정 표현은 "이 앱은 L2 대상이며, L2 기준 **충족/미충족**" — 자기 기준선 대비 통과 여부만
말한다. 인증마크 발급 기준도 점수가 아니라 **"해당 보호 수준 필수 전항 충족 + Critical 0"**.
'등급'이라는 말은 쓰지 않는다(서열 오독 방지) — '보호 수준' 또는 '기준선'으로 부른다.

|---|---|---|
| H-edu-fit | 교육적 적절성 — 발달단계 적합, 낙인·서열화 없음 | 3 |

## 14. 인증 배지 설계 (2026-08-28 팀 구현 반영)

배지 이미지는 복사 가능하므로, 설계의 핵심은 "예쁜 배지"가 아니라 **검증 가능한 배지**다.
배지는 표시일 뿐이고 실체는 검증 가능한 발급 기록이다.

- **현재 구현(팀 — EAS 서명)**: 서버(Vercel)가 요청된 커밋 SHA를 **직접 내려받아 규칙 점수를
  재계산**하고, 80점 이상·Critical 0일 때만 EAS(Ethereum Attestation Service) offchain v2
  형식의 EIP-712 서명을 발급한다. 가스리스(트랜잭션·ETH 불필요), 브라우저가 보낸 점수는
  신뢰하지 않음. 서명·기록은 PostgreSQL 저장, 공개 검증 API가 서명을 재계산. 로컬 폴더
  심사는 서버가 원본을 독립 확인할 수 없어 자동 발급 제외.
- **경량 경로(공개 대장)**: git 이력 기반 공개 인증 대장(edusafe-registry) + SVG 배지 —
  서버 없이 동작하는 검증 경로로 병행.
- **유효 조건 2겹**: 구조적(심사 커밋과 다르면 무효) + 시간적(만료·재심사 연동).
- **열린 논점(팀 논의 필요)**: 현 구현의 Silver/Gold 등급 표시는 "등급 없음(교사 앱 서열화
  방지)" 원칙과 긴장 관계 — 자동 점수 임계는 유지하되 표시 방식 합의 필요. AI·사람 심사
  판정은 서버 불변 심사 기록 도입 전까지 서명 기준에서 제외(현 구현의 명시적 한계).
- **발급 주체의 단계**: 파일럿 단계 마크는 "심사 통과 기록"이며 법적 인증이 아님을 명시.
  교육청 도입 후 기관 명의 발급 — 교육 분야 표준 Open Badges(1EdTech) 호환 필드 유지.
