# Implementation Plan — 에듀 세이프 해커톤 빌드

2026-08-27 작성 (행사 전 사전 기획 — 대회 규정 허용 범위). 설계 결정은
`docs/해커톤-design-plan.md`, 루브릭 전문·화면 설계는 `docs/해커톤-기획서.md`.
이 문서는 **작업의 설계**다: 어떤 순서로, 각 단계의 완료를 무엇으로 증명하나.
**범위: 트랙 2(심사 앱)의 코어 재구축만 다룬다.** 트랙 1(스킬)은 별도 문서 체계·담당.

## 0. 실행 원칙

1. **테스트 우선(TDD)**: 각 태스크는 완료 기준이 테스트다. 코드보다 검증 장치를 먼저 만든다.
2. **작업 단위 커밋**: 태스크 1개 = 커밋 1개 이상. 커밋 타임스탬프가 "현장에서 만들었다"의
   증빙이자 진행 로그다 (17:30 정각의 빈 첫 커밋으로 시작).
3. **시연 경로 우선**: 불러오기→스캔→판정→보고서 한 줄기를 끝까지 완성한 뒤 폭을 넓힌다.
4. **데이터 → 순수 로직 → 외부 통신 → UI** 순서: 앞 단계의 테스트 위에 뒷 단계를 쌓는다.
5. 기존 프로토타입 코드베이스는 열지 않는다. 참조는 이 기획 문서 3종과 머릿속 지식만.

## 4. 규정 준수·증빙 절차

- 17:30 이전에는 코딩·코드 생성 프롬프트 입력을 하지 않는다. 사전 준비물은 기획 문서 3종뿐.
- 새 저장소의 커밋 이력(작업 단위, `Co-Authored-By: Claude` 투명 표기)이 검증 자료.
- 발표 고지 문구(기획서 12장)를 그대로 사용: 기존 프로토타입의 존재를 밝히고,
  "오늘 출품작은 17:30부터 새 저장소에서 처음부터"임을 두 저장소의 커밋 기록으로 증명.
