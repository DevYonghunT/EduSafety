# Design Plan — 에듀 세이프 해커톤 빌드

2026-08-27 작성 (행사 전 사전 기획 — 대회 규정 허용 범위). 제품 전체 기획은
`docs/해커톤-기획서.md`, 작업 분해는 `docs/해커톤-implementation-plan.md`.
이 문서는 **설계 결정의 기록**이다: 무엇을, 왜, 어디까지.

## 1. 전제 선언 (설계의 출발점)

> 자가점검은 "정직한 답변"을 전제하지만, 심사는 "통과하고 싶은 사람"을 전제한다.

따라서 이 시스템의 모든 판정은 자기신고가 아니라 **코드에서 수집한 증거**에 근거해야 하며,
증거가 없는 판정은 판정이 아니다. 이 전제에서 아래 모든 결정이 파생된다.

## 2. 문제 정의

- 바이브 코딩으로 교사 제작 앱이 급증하지만, 학생 개인정보·보안을 검증할 공적 체계가 없다.
- 「초·중등교육법」 제29조의2(2026-03-01 시행)가 학습지원 SW의 기준 준수·학운위 심의를
  의무화했으나, 현행 '기준 충족 확인'은 업체 자기신고 체크리스트와 학교의 육안 확인에
  의존한다. **법이 요구하는 심의의 증거 인프라가 비어 있다.**

## 3. 목표와 성공 기준 (이번 해커톤 세션)

| 목표 | 성공 기준 |
|---|---|
| 심사 시연 경로 1개 완주 | 불러오기 → 규칙 스캔 → AI 판정 → 심사자 확정 → 보고서가 실제 앱 1건에 대해 동작 |
| 신뢰성 원칙의 코드 강제 | 근거 없는 판정 강등·보류 규칙이 **테스트로 증명**됨 |
| 규정 준수의 증명 | 새 저장소 첫 커밋부터 작업 단위 커밋 — 타임스탬프가 곧 증빙 |

## 4. 쟁점 → 결정

| 쟁점 | 결정 | 이유 |
|---|---|---|
| 판정 주체 | 자동 증거 수집 + **사람이 최종 판정** | 완전 자동화는 공적 심사의 책임 소재를 흐림 |
| 자기신고 | 배제 — 개인정보 수합 구조도 AI가 코드에서 직접 분석 | 전제 선언 참조 |
| AI의 역할 | 판정자가 아니라 **증거 수집자** (판정 초안 + 근거 인용) | 최고 모델도 취약점 탐지 정확도가 완전하지 않음 — 구조로 보완 |
| 심사 무결성 | 커밋 SHA(폴더 제출은 SHA-256 지문)에 심사를 고정 | "이 심사는 커밋 X에 대한 것"이 실제로 성립해야 변조 방지 |
| 입력 경로 | GitHub 공개 저장소 우선, 폴더 업로드는 여유 시 | 시연 경로 1개 완주가 우선 |
| AI 키 관리 | 심사자 키를 브라우저 localStorage에만 — **하드코딩 절대 금지** | 공개 앱에 키를 넣는 것은 자체 루브릭 R-secrets 위반 |
| 개인정보 전송 | 데이터 파일 미전송·비밀키 마스킹 후 AI 호출 | 심사 도구가 스스로 개인정보 원칙을 지켜야 함 |
| 판정값 | 충족/미충족/판단불가/해당없음 4값 — 확신 없으면 판단불가 | 과잉 판정 방지, 판단불가는 시스템의 정직함 |
| 제품 구조 | **투트랙** — 스킬(교사용 거울, 별도 문서 체계) + 심사 앱(기관용 저울, 본 계획) | 자가점검과 공적 심사는 사용자·권한·산출물 지위가 다름 — 섞으면 둘 다 망가진다 |
| 결과 표현 | 단일 점수 폐지 — **카테고리별 상태(8분류, 최악 판정) + 행동 중심 요약**, 종합판정 3값 유지 | 단일 숫자는 행동을 안내하지 못하고 정밀성 착시·서열화를 유발. 스킬(행동 중심)과 결 일치 |
| 최소 기준선 | **위험 기반 3수준 보호선** — L0 공통 기본선 / L1 개인정보 보호선 / L2 민감·공정성 보호선. 수준은 앱 기능에서 자동 도출, 판정은 자기 수준 대비 충족 여부 | "등급 없음" 원칙과 양립 — 앱 간 서열이 아니라 위험별 요구 수준 (ASVS 수준 개념·교육부 선정기준 적용대상 논리와 정렬) |

## 5. 신뢰성 원칙 → 강제 장치 매핑

원칙은 문서에 두면 잊히고, 코드에 두면 실패한다(테스트가 깨진다). 각 원칙이 어디서
강제되는지를 설계에 포함한다.

| # | 원칙 | 강제 장치 |
|---|---|---|
| 1 | 근거 인용 없는 충족/미충족은 판단불가로 강등 | 검증 함수(validateJudgments) + 단위 테스트 |
| 2 | AI 응답 누락 항목은 판단불가로 채움 | 같은 함수 |
| 3 | 판단불가가 남으면 종합 판정은 무조건 '보류' | 집계 함수(computeSummary) + 테스트 |
| 4 | 최종 판정은 심사자 — 번복은 사유와 함께 기록 | 오버라이드 > AI > 수동의 판정 우선순위 |
| 5 | 심사는 커밋 SHA/콘텐츠 지문에 고정 | 로드 시 SHA 고정 조회, 보고서에 각인 |
| 6 | 심사 대상 코드는 신뢰할 수 없는 입력 | 텍스트 노드 렌더만(HTML 실행 금지) |
| 7 | 데이터 파일 미전송·비밀키 마스킹 후 AI 전송 | 전송 전 redact 단계 + 테스트 |
| 8 | AI 분석 범위의 정직한 고지 (조용한 절단 금지) | 우선순위 선별 + 커버리지 % 표시 |

## 6. 비범위 — 이번 세션에서 만들지 않는 것

**트랙 1 스킬(교사용 자가점검 — 별도 문서 체계·담당)**, 서버 인프라(계정·제출함·DB),
인증 배지 발급(EAS/공개 대장), 성취기준 전체 선택기, 루브릭 개정 도구.
— 로드맵·투트랙 구조로 발표에서 언급하되 구현하지 않는다.

## 7. 검증 계획

1. **세션 중**: 태스크마다 테스트 게이트(구현 계획서 참조), 마지막에 실제 앱 1건 라이브 심사.
2. **세션 후**: 파일럿 실심사 5~10건으로 판정 정확도·판단불가율 측정 → 루브릭 개정.
   이 데이터가 교육청 제안의 근거가 된다.

## 8. 열린 논점 (결정 보류 — 팀 논의)

- **루브릭 코어 통합**: 스킬(1.2-skill, 37항목)과 앱(v1.3, 31항목)의 정본 단일화 —
  대조표(기존 프로토타입 저장소 `docs/루브릭-대조표.md`) 기반 분류 회의 (코어/스킬 전용/앱 전용)
- 인증마크의 등급 표시(Silver/Gold) vs "등급 없음(서열화 방지)" 원칙의 조화 —
  **점수 폐지 결정으로 EAS 발급 임계(80점) 재논의 필요** (대체안: "해당 보호 수준 필수 전항
  충족 + Critical 0")
- AI 표시·오류 고지 항목(S-ai-transparency/fallibility)의 스킬 추가 여부 — 모의고사·수능 불일치 해소
- AI·사람 심사 판정을 서명 발급 기준에 포함하는 시점(서버 불변 심사 기록 도입 이후)
