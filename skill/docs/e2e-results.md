## Step 1 — 설치 ✅

`edusafe/` 를 `~/.claude/skills/edusafe/` 에 복사했다.

- 파일 11개가 전부 복사됐다.
- **설치본의 지문이 배포본과 일치한다**: `sha256:da7c4ee9…` (원본 = 설치본).
- Claude Code 가 재시작 없이 스킬을 인식했다. README 의 "도구를 새로 실행하면 인식됩니다" 는 보수적인 안내이고, 실제로는 더 빨리 잡힌다.

## Step 2 — 픽스처 대화형 ❌ 미수행

수행하지 못했다. 이유: 마감(2026-08-29) 시간 부족. 대화형 실행에 쓸 사람의 시간을 실제 앱(Step 6)에 쓰기로 결정했다. Step 6 이 같은 성질(대화형·사람이 승인·사람이 답변)의 더 강한 시험이라 판단했다.

## Step 3 — 비대화형 (출시 게이트, REQ-12.7) ❌ 미수행

### 2회차 — 관측을 붙였고, 원인이 보였다

1회차는 `-p` 기본 출력이 **끝나야 한 번에 나오는** 탓에 "멈춘 것"과 "일하는 중"을 구별할 수 없었다. `--output-format stream-json --verbose` 로 다시 돌리자 4분 30초 동안 도구 호출 27번이 보였고, 그 대부분이 규칙 데이터 읽기였다(`items.json`·`session.json`·`moe-checklist.json`·`report.contract.json`·`scan-rules.mjs`).

**판정을 시작하기 전에 스킬 자신의 규칙 데이터를 통째로 읽는 구간이다.** 멈춘 것이 아니었다.

### 남은 위험

이 게이트가 닫히지 않은 채로는 다음을 모른다.

1. 4~6단계가 **사람 없이** 끝까지 가는지 (Step 6 은 사람이 있는 상태에서 완주했다)
2. `coverage.build` 가 `{skipped, non-interactive}` 로 기록되는지
3. `coverage.evidence`·`coverage.teacher` 가 `skipped` 이고도 보고서가 완성되는지
4. 비대화형 판정 수치가 대화형과 같은지

**출시 판단**: REQ-12.7 이 이것을 출시 게이트라고 못박았으므로, 이 배포본은 **게이트를 통과하지 못한 상태**다. 그 사실을 안내 페이지나 README 에서 숨기지 않는다.

## Step 4 — 기존 빌드 산출물 ✅ Step 6 에서 실질 통과

전용 회차는 돌리지 못했으나, Step 6 이 정확히 이 경로를 탔다. 교사가 빌드 실행을 승인하지 않았고 `.next` 가 이미 있었다.

```json
  "error": "빌드를 실행하지 않고 기존 .next 산출물을 읽기 전용으로 스캔했습니다.
            산출물이 현재 소스와 일치한다는 보장은 없습니다
            (.next 보다 새로 수정된 소스 파일은 없었습니다)."
}
```

계획서가 요구한 `{ status: "ran", reason: "prebuilt-artifact" }` 와 REQ-5.15 의 안내 문구가 그대로 나왔다. `build_artifact_digest` 도 기록됐다.

### D-1. 계획서가 존재하지 않는 CLI 플래그를 지시했다 — 고침

| | |
|---|---|
| 분류 | **문서가 틀렸다** |
| 내용 | Task 9 Step 3 이 `claude -p "/edusafe" --cwd <픽스처 경로>` 라고 지시하는데, `--cwd` 플래그는 claude 2.1.216 에 없다. |
| 조치 | 계획서를 먼저 고쳤다. 작업 디렉터리는 프로세스의 cwd 로 정해진다는 것, 관측을 위해 `--output-format stream-json` 이 필요하다는 것, 스캔·렌더가 node 로 도는 만큼 `Bash(node *)` 허용이 필요하다는 것을 함께 적었다. |

### D-2. 계약 밖 파일 — 해소

실행 중 `edusafe-report/.staging-path.txt` 가 생기는 것을 관찰했으나, Step 6 완주 후 확인한 결과 **6단계 staging 교체 시 정리된다.** 최종 산출물에 계약 밖 파일은 없다. 결함이 아니다.

### D-3. 실행 시간 — 해소

픽스처 13.7분이 우려됐으나, 실제 앱(100배 규모)에서 22분이었다. 고정비가 지배적이고 규모에 따라 잘 늘어나지 않는다. 다만 **22분은 교사가 기다리기에 짧지 않다** — 절차서나 README 가 예상 소요 시간을 미리 알려 주지 않는 것은 v0.2 의 개선 대상이다.

| | |
|---|---|

### D-5. "계획대로 아직 시점이 아니다" 를 표현할 판정이 없다 ⚠️ 미해결

**이번 검증의 최대 수확이다. 원인은 구현이 아니라 문서에 있다.**

| | |
|---|---|
| 분류 | **문서가 비어 있었다** |
| 심각도 | 상 항목 false positive 2건 — 교사에게 "배포 전 반드시 수정" 으로 표시된다 |
| 상태 | **v0.1 에서 고치지 않는다.** 아래 "왜 고치지 않았나" 참조 |

#### 무엇이 일어났나

| 항목 | 교사 답변 | 스킬 판정 |
|---|---|---|
| `R-under14` 만 14세 미만 동의 | "실제로 받을 예정, 서면 가정통신문 보낼거야" | `fail` / `high` → 🔴 |
| `H-school-approval` 학교운영위 심의 | "정규 교과 수업에 사용하고, 심의는 9월에 거친 뒤 사용할 예정" | `fail` / `high` → 🔴 |

둘 다 **교사의 계획이 적법하고 순서도 옳다.** 동의는 학생 실사용 전에 서면으로 받을 예정이고(시행령 제17조의2 가 인정하는 방법), 심의도 사용 개시 전에 거칠 예정이다.

#### 스킬은 상황을 정확히 이해하고도 틀린 라벨을 붙였다

스킬 자신의 `reasoning` 이 그것을 말한다.

> `R-under14`: "코드 게이트가 미동의 계정의 처리를 막고 있어 **지금 침해가 일어나고 있지는 않다**"
> `H-school-approval`: "**이 판정은 새로운 문제 제기가 아니라** 그 계획을 보고서에 못 박아 두는 것이다"

서술은 옳은데 판정값이 `fail` 이다.

#### 원인 — 구현이 아니라 §7.6 표와 §7 의 공백

`H-school-approval` 은 구현의 잘못이 전혀 없다. spec §7.6 결정표를 **그대로** 실행했다.

```
| H-school-approval | 적용 트리거 ①·② 중 하나 해당 (정규 교과 사용) | high |
```

이 줄은 "정규 교과에 쓰나?" 만 묻고 **"심의를 사용 개시 전으로 잡아뒀나?" 를 조건에 넣지 않았다.** 그래서 순서를 옳게 잡은 교사도 `low → high` 로 승격돼 최상단에 올라간다.

`R-under14` 는 더 근본적이다. **"배포 전 점검" 스킬이 "배포 전에 하겠다" 는 답을 `fail` 로 잡는 것은 순환이다.**

한 줄로 줄이면: **스킬이 "아직 안 했다" 와 "계획대로 아직 시점이 아니다" 를 구분하지 못한다.**

`[REQ-7.1]` 은 판정값을 4개로 못박으면서 "5번째 값을 두지 않고 **사유(`reason`)로 구분한다**" 고 했다. 그런데 §7 이 그 `reason` 규칙을 만들지 않았다. `demotion_reason` 필드는 계약에 이미 있고 두 항목 모두 `null` 이었다 — 기제는 있는데 규칙이 없었다.

#### 왜 v0.1 에서 고치지 않았나

1. **검증할 수 없다.** 판정 규칙을 바꾸면 22분짜리 실제 실행과 사람의 답변을 다시 받아야 옳은지 안다. 마감일에 그 시간이 없다.
2. **지금 틀린 방향이 안전한 쪽이다.** false positive 는 교사가 헛일을 하는 것이고, 급하게 고쳐 false negative 가 되면 교사가 위반을 안고 배포한다. spec §12.5 가 실격으로 규정한 것은 후자다.
3. 검증 없는 판정 규칙 변경은 이 저장소의 규율(문서 → 린터 → 테스트 → 실행 검증)을 건너뛰는 것이다.

#### v0.2 에서 할 것

- §7 에 규칙을 만든다: 확인 세션 답변이 **계획을 밝히고 그 시점이 사용 개시 전**이면, `verdict` 는 `fail` 로 두되 `effective_severity` 를 강등하고 `demotion_reason` 에 근거를 남긴다. 그러면 🔴 가 아니라 ⚪ 참고나 ✍️ 교사 확인으로 렌더된다.
- §7.6 의 `H-school-approval` 행 조건에 "사용 개시 전 심의 계획이 확인되지 않은 경우" 를 넣는다.
- 확인 세션 질문을 시점까지 묻도록 다듬는다("받으셨나요?" → "받으셨나요, 아니면 언제 받으실 예정인가요?").
